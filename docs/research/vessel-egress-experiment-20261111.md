## 預先固定的實驗規則

1. 實驗 ID `vessel-20261111`，只使用 worker 原定的恢復探查，依序為原出口、日本、新加坡，每條路徑最多預留一筆，全部最多三筆。
2. 共用既有全域鎖、每小時上限、請求間隔、每日新月份探查、滾動 24 小時最多三次恢復探查，以及所有 Retry-After／退避。沒有另開獨立額度桶。
3. 三筆都取正常佇列中真正待補的網域，沿用重要性排序，不為比較重抓同一站。所有裝置身分與請求標頭沿用原值，沒有輪換身分。
4. 只有已預留 `recovery_probe=1` 的請求會參加；一般收集不會為了完成比較額外使用出口。程式在送出前將實驗 ID 與出口寫入既有 `sends.response_meta`，pending／錯誤／拒絕都占一次，重啟不重做。
5. 任一 HTTP 401／403／429 或明確 quota exceeded 都回到同一套全域冷卻；不立即換出口重試。網路錯誤也不換路徑補送。
6. 仍按既有恢復條件，三次連續可解析並已保存的回應才恢復一般限速。實驗用完後，正常排程回到原出口；不自動建立第二輪，也不變更實驗 ID 來重置次數。
7. 原每日 15:40 監看維持停用。

## 實作與可觀測性

- `src/egress-experiment.ts`：固定順序、三筆上限、預留紀錄及逐請求傳輸。
- `src/worker.ts`：只為原有 runner 注入實驗傳輸；runner 仍先確認政策再發出請求。
- `sends.response_meta`：`egressExperiment`、`egressRoute`、可取得的 Retry-After／限額標頭，以及成功解析保存後的 `latestMonth`、`latestProfileMonth`。不記錄裝置識別或請求憑證。
- `/api/v1/status.egressExperiment` 與 `/status/`：顯示預留數、下一出口、實際 HTTP 狀態、結果及收到月份。查詢本身不打 Similarweb。
- `TRAFFIC_EGRESS_EXPERIMENT=vessel-20261111` 啟用這一輪；清空可停用。程式不重設任何既有冷卻。

原出口與東京在 sky-server 以 curl 傳輸；東京只綁定 `10.8.1.6`。新加坡經 SSH 在 mint-mbp 以 curl 綁定 `10.8.1.8`。既有 Vessel source policy routing 與 unreachable default 保留；綁定失敗不回退本機。curl 不載入使用者設定、不使用代理環境、不跟隨轉址、不自動重試，強制 IPv4／HTTP/1.1，並限制時間與輸出大小。標頭透過 stdin 傳遞，不出現在程序命令列。

這是初步連通性比較：網域與採樣時間不同，而且 sky-server 為 curl 8.18 / OpenSSL 3.5.5，mint-mbp 為 curl 8.5 / OpenSSL 3.0.13。即使回應不同，也不能完全歸因於 IP；即使三條都成功，也不能推論各 IP 額度獨立或總額度增加三倍。
